# DDIBS V5 Final Review

## 1. 문서 목적

이 문서는 DDIBS V5에서 수행한 작업과 그 의미를 정리한 마감 문서다.

V4까지의 DDIBS가
- 핵심 플로우 완성
- 관리자 운영 조회/API 확장
- 관리자 프론트 데모 레이어
- 시연 문서와 버전 문서 정리

까지를 통해 **동작하고, 보여줄 수 있고, 설명할 수 있는 상태**를 만드는 데 집중했다면,

V5는 그 위에
- 시간 정책의 경계 조건 정리
- 배치 트랜잭션 경계 재설계
- 락 획득 순서 점검
- 부분 실패 후 재실행 안정성 검증
- 운영 예외 추적 로그 보강

을 더해, DDIBS의 백엔드 완성도를 한 단계 더 높이는 단계였다.

즉 V5의 핵심은 기능을 더 많이 넣는 것이 아니라,  
이미 완성된 DDIBS의 **정합성 · 동시성 · 배치 운영성 · 설명 가능성**을 더 단단하게 만드는 데 있었다.

---

## 2. V5 목표

V5의 목표는 아래 5가지였다.

1. **홀드 만료 경계시각 정책을 명확히 정리한다.**
2. **배치 트랜잭션 경계를 줄여 온라인 흐름과의 간섭을 낮춘다.**
3. **락 획득 순서를 실제 코드 기준으로 점검하고 표준화 포인트를 정리한다.**
4. **부분 실패 후 재실행 시나리오를 테스트로 보강한다.**
5. **운영 예외 발생 시 서버 로그에서 원인 추적이 가능하도록 보강한다.**

정리하면 V5는  
“새 화면/새 기능 추가”가 아니라,  
**백엔드 운영 품질과 정책 완성도를 높이는 버전**이었다.

## 3. V5 완료 항목

## 3.1 홀드 만료 경계시각 정책 정리

V5 초반에는 Codex 리뷰를 바탕으로, 홀드 만료 시각의 경계 조건을 점검했다.

기존 구현은 다음과 같은 strict 기준에 가까웠다.

- 도메인: `currentTime.isAfter(expiresAt)`
- 조회 쿼리: `expiresAt < now`

이 상태는 코드끼리 일관성은 있었지만,  
정확히 `expiresAt == now`인 경우를 만료로 보지 않는 정책이라  
실무 설명력 측면에서는 아쉬움이 있었다.

### 변경 내용
- 홀드 만료 기준을 **`currentTime >= expiresAt`** 로 정리
- `HoldReservation.isExpiredAt(...)` 비교식 수정
- 만료 대상 조회 쿼리도 같은 기준으로 정렬
- `Clock` 도입으로 배치 시간 기준을 주입 가능하게 정리
- 경계시각 테스트 추가
    - `now < expiresAt`
    - `now == expiresAt`
    - `now > expiresAt`

### 의미
- 홀드 TTL 정책을 더 명확하게 설명할 수 있게 됨
- 도메인 / 배치 / 테스트가 같은 시간 기준으로 정렬됨
- 시간 경계값 테스트를 안정적으로 재현할 수 있게 됨

## 3.2 배치 트랜잭션 경계 재설계

V5에서 가장 큰 구조 변경은 배치 트랜잭션 경계 정리였다.

기존 구조는 홀드 만료 배치와 정산 생성 배치 모두  
“후보 조회 → 루프 전체 처리”가 하나의 큰 트랜잭션 안에서 돌아가는 형태였다.

이 구조는 구현은 단순하지만, DDIBS처럼
- 주문
- 결제
- 홀드 만료
- 정산 생성

이 함께 존재하는 시스템에서는 다음과 같은 아쉬움이 있었다.

- 배치 실행 시간이 길어질수록 락 점유 시간이 길어질 수 있음
- 중간 한 건 실패 시 롤백 범위가 커짐
- 부분 실패 후 재실행 설명력이 약함

### 변경 내용
#### 홀드 만료 배치
- `HoldExpirationBatchService`를 **오케스트레이터 역할**로 정리
- 실제 만료 처리 로직을 `HoldExpirationItemProcessor`로 분리
- 건별 처리 메서드에 `REQUIRES_NEW` 적용
- 결과 집계를 위한 `HoldExpirationProcessingResult` 추가

#### 정산 생성 배치
- `SettlementBatchService`를 **오케스트레이터 역할**로 정리
- 실제 정산 생성 로직을 `SettlementItemProcessor`로 분리
- 건별 처리 메서드에 `REQUIRES_NEW` 적용
- 정산 후보 조회를 `Order` 엔티티 전체가 아니라 `orderId` 중심으로 경량화

### 의미
- 배치 전체 단일 트랜잭션 구조를 줄였다
- 한 건 실패가 전체 배치에 미치는 영향을 줄였다
- 배치 서비스와 건별 처리 서비스의 역할이 더 분명해졌다
- 홀드 만료 배치와 정산 생성 배치가 같은 패턴으로 정리되어 설명 가능성이 좋아졌다

## 3.3 락 획득 순서 점검 및 판단 정리

Codex 리뷰의 High 항목 중 하나는  
결제 실패 / 홀드 만료 / 주문 생성 경로 사이의 락 순서 불일치 가능성이었다.

V5에서는 관련 write 경로의 실제 코드를 다시 확인해  
락 획득 순서를 정리했다.

### 확인한 주요 경로
- 주문 생성
- 결제 성공
- 결제 실패
- 홀드 만료 배치
- 정산 생성 배치

### 확인 결과
#### 기존 주문 변경 경로
- 결제 실패: `Order → HoldReservation → LaunchVariant`
- 홀드 만료 배치: `Order → HoldReservation → LaunchVariant`

즉 기존 주문/홀드를 다루는 핵심 재고 관련 경로끼리는  
락 순서가 이미 일치하고 있었다.

#### 주문 생성 경로
- `LaunchVariant`를 먼저 선점
- 이후 `Order`, `HoldReservation` 생성

이 경로는 기존 주문 수정 경로가 아니라  
**신규 주문/홀드 생성 경로**이므로 성격이 달랐다.

### 판단
- 현재 코드 기준으로는 **즉시 리팩토링이 필요한 High severity 상태로 보긴 어렵다**
- 다만 락 순서 정책은 문서화할 가치가 충분하다

### 정리한 정책
- 기존 주문을 변경하는 재고 관련 write 경로는  
  **`Order → HoldReservation → LaunchVariant`** 순서를 따른다
- 주문 생성은 신규 생성 예외 경로로 본다
- 향후 기존 주문과 재고를 함께 수정하는 신규 write 경로는  
  위 표준 순서를 따르도록 한다

### 의미
- 락 정책을 “추측”이 아니라 실제 코드 기준으로 설명할 수 있게 됨
- 과도한 리팩토링 없이도 정책 문서화 포인트를 확보함

## 3.4 부분 실패 후 재실행 테스트 보강

V5에서 특히 중요했던 보강 중 하나는  
“배치가 중간 실패 후 재실행될 때 정확히 어떻게 수렴하는지”를 테스트로 증명한 것이다.

기존에도 배치 테스트와 멱등성 테스트는 있었지만,  
운영에서는 “일부 처리 후 예외 → 재실행” 시나리오가 더 현실적이다.

### 추가한 테스트 시나리오
#### 홀드 만료 배치
- 만료 대상 2건 준비
- 두 번째 건 처리에서 1회 강제 실패
- 1차 실행 후:
    - 첫 번째 건만 EXPIRED / 주문 만료 / 재고 복구 완료
    - 두 번째 건은 아직 ACTIVE / CREATED / 재고 미복구
- 2차 재실행 후:
    - 두 번째 건도 정상 만료 처리
    - 이미 처리된 첫 번째 건은 다시 처리되지 않음

#### 정산 생성 배치
- 확정 주문 2건 준비
- 두 번째 주문 정산 생성 시 1회 강제 실패
- 1차 실행 후:
    - 첫 번째 주문만 정산 생성
    - 두 번째 주문은 정산 미생성
- 2차 재실행 후:
    - 두 번째 주문도 정산 생성
    - 중복 정산은 생성되지 않음

### 의미
- `REQUIRES_NEW` 기반 건별 트랜잭션 구조가 실제로 기대한 대로 동작함을 검증함
- DDIBS의 배치가 “부분 성공 후 재실행 가능한 구조”라는 점을 테스트로 설명할 수 있게 됨
- 운영 재기동/재실행 시나리오에 대한 설득력이 높아짐

## 3.5 운영 예외 추적 로그 보강

V5 마지막 단계에서는 예외 응답 구조보다  
**서버 로그 관점의 추적성**을 보강하는 데 집중했다.

기존 `GlobalExceptionHandler`는 응답 포맷은 잘 정리되어 있었지만,  
운영 중 예외 발생 시 서버 로그에 남는 정보가 부족했다.

### 변경 내용
- `GlobalExceptionHandler`에 `@Slf4j` 추가
- `BusinessException` → `warn` 레벨 로그 추가
- validation 계열 예외 → `warn` 레벨 로그 추가
- 인증 / 인가 예외 → `warn` 레벨 로그 추가
- 예상하지 못한 일반 예외 → `error` 레벨 + stack trace 로그 추가

### 유지한 점
- `ErrorResponse` 포맷은 변경하지 않음
- `BusinessException + ErrorCode` 구조 유지
- API 응답 계약을 흔들지 않음

### 의미
- 운영 장애 시 URI, 에러코드, 메시지, 예외 타입 등을 로그에서 추적 가능해짐
- DDIBS처럼 상태 전이와 정합성이 중요한 시스템에서 RCA 설명력이 좋아짐
- 응답 설계와 로그 설계를 분리해서 단계적으로 개선함

## 4. V5에서 중요했던 설계 판단

## 4.1 시간 정책은 비교 연산자만 바꾸는 것으로 끝내지 않았다

V5 Step 1에서는 단순히 `>`를 `>=`로 바꾸는 데서 끝내지 않고,  
`Clock` 도입과 경계시각 테스트까지 같이 정리했다.

이는 “코드 한 줄 수정”보다  
**정책을 테스트 가능하고 설명 가능하게 만든다**는 쪽에 더 가까운 판단이었다.

---

## 4.2 배치 구조는 Hold / Settlement를 같은 패턴으로 맞췄다

처음에는 정산 배치를 `TransactionTemplate`로 우회하는 방향도 잠깐 검토했지만,  
최종적으로는 Hold 만료 배치와 동일하게

- 오케스트레이터
- ItemProcessor
- `REQUIRES_NEW`

구조로 정리했다.

이 판단 덕분에:
- 프로젝트 구조 일관성이 좋아졌고
- 문서/면접 설명도 더 쉬워졌다.

---

## 4.3 락 순서 문제는 “즉시 리팩토링”보다 “실제 코드 기준 판단”을 택했다

락 순서 이슈는 중요한 문제의식이었지만,  
현재 코드 기준으로는 기존 주문 변경 경로의 락 순서가 이미 정렬되어 있었다.

그래서 V5에서는 무리하게 구조를 또 변경하기보다,
- 실제 코드 기준 락 순서 확인
- 예외 경로 구분
- 문서화 포인트 정리

로 마무리하는 것이 더 적절하다고 판단했다.

이는 DDIBS의 우선순위인
**정합성 + 설명 가능성 + 과도하지 않은 구조**와도 잘 맞았다.

---

## 4.4 Step 5는 응답 포맷보다 운영 로그를 우선했다

`ErrorResponse`를 더 바꾸거나, traceId/MDC까지 확장하는 길도 있었지만  
V5에서는 그보다 로그 보강만 수행했다.

즉 응답 계약은 흔들지 않고,  
운영 추적성을 먼저 올리는 쪽으로 범위를 통제했다.

이 판단 덕분에 V5는 과도하게 커지지 않고,  
딱 필요한 백엔드 품질 보강에 집중할 수 있었다.

V5는 **백엔드 내부 정책과 운영 품질**을 더 단단하게 만든 단계였다.

## 6. V5 기준 현재 강점

V5를 마친 현재 DDIBS의 강점은 아래와 같다.

- 핵심 플로우 2개가 완성되어 있다
- 홀드 만료 경계시각 정책이 문서/코드/테스트로 정리되어 있다
- 배치 서비스가 오케스트레이터 + ItemProcessor 구조로 정리되어 있다
- 배치 건별 처리에 `REQUIRES_NEW`가 적용되어 있다
- 부분 실패 후 재실행 시나리오를 테스트로 검증했다
- 락 획득 순서를 실제 코드 기준으로 설명할 수 있다
- 운영 예외 발생 시 서버 로그에서 원인 추적이 가능해졌다
- 관리자 운영 조회/API, 프론트 데모, 문서화까지 모두 갖춘 상태다

즉 DDIBS는 이제 단순히 “동작하는 드롭 런치 백엔드”를 넘어,  
**운영 품질과 설명 가능성까지 갖춘 백엔드 포트폴리오**에 더 가까워졌다.

## 8. 회고

V5에서 가장 중요했던 점은,  
DDIBS를 “핵심 플로우가 구현된 프로젝트”에서  
**운영 품질까지 설명 가능한 프로젝트**로 한 단계 더 올린 것이다.

특히
- 홀드 만료 경계시각을 `Clock`과 경계 테스트로 정리한 점,
- 배치 트랜잭션 경계를 오케스트레이터/ItemProcessor 구조로 재설계한 점,
- 부분 실패 후 재실행 시나리오를 테스트로 증명한 점

은 DDIBS답게 아주 의미 있는 보강이었다.

또한 락 순서 문제를 무리하게 구조 변경으로 가져가지 않고,  
실제 코드 기준 판단과 정책 문서화 포인트로 정리한 것도  
과도한 리팩토링을 피한 좋은 선택이었다.

즉 V5는 새 기능을 크게 추가한 버전은 아니지만,  
**DDIBS의 백엔드 깊이와 설명력을 확실히 끌어올린 버전**이었다.

---

## 9. 한 줄 결론

DDIBS V5는  
**시간 정책, 배치 트랜잭션 경계, 재실행 안정성, 운영 예외 추적성**을 정리하고 보강해  
프로젝트의 백엔드 완성도를 한 단계 더 높인 단계였다.
