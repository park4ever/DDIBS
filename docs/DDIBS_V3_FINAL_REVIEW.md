# DDIBS V3 Final Review

## 1. 문서 목적

이 문서는 DDIBS V3에서 수행한 작업과 그 의미를 정리한 마감 문서다.

V1이 **핵심 플로우 완성**,  
V2가 **테스트 재현성 / 배치 운영성 / 관리자 조회 고도화**,  
V3는 그 위에 **운영 조회 확장 + 최소 프론트엔드 데모 레이어 + 시연 자료 정리**를 더해  
DDIBS를 실제로 “보여줄 수 있는 포트폴리오” 형태로 마감하는 단계였다.

즉 V3의 핵심은 새로운 커머스 기능을 무작정 늘리는 것이 아니라,  
이미 완성한 DDIBS의 핵심 메시지를 **운영 화면과 시연 문서로 더 분명하게 전달할 수 있게 만드는 것**이었다.

---

## 2. V3 목표

V3의 목표는 아래 3가지였다.

1. **관리자 운영 조회를 주문 중심에서 정산 / 발매·재고까지 확장한다.**
2. **백엔드 운영 API를 직접 시연할 수 있는 최소 프론트엔드 데모 레이어를 만든다.**
3. **시연 문서와 시퀀스 다이어그램을 정리해 DDIBS의 설명 가능성을 높인다.**

정리하면 V3는
“기능 추가 단계”라기보다,
**보여주기 / 설명하기 / 포트폴리오 마감 완성도**를 높이는 단계였다.

---

## 3. V3 완료 항목

## 3.1 관리자 정산 조회/API 고도화

V2까지는 관리자 주문 조회가 우선 보강된 상태였고,  
정산 조회는 상대적으로 최소 수준에 가까웠다.

V3에서는 정산 조회를 운영 관점에서 더 실용적으로 사용 가능하도록 정리했다.

### 주요 개선 내용
- QueryDSL 기반 관리자 정산 조회 구현
- 검색 조건, 페이징, 정렬 지원
- 정산 코드 / 주문 코드 / 판매자 ID / 상태 / 기간 조건 조회 지원
- `AdminSettlementQueryService` 및 관련 DTO 정리
- 정산 조회 통합 테스트 작성

### 의미
- 정산을 단순 배치 결과가 아니라, **운영자가 추적 가능한 데이터**로 보여줄 수 있게 됨
- 결제 성공과 정산 생성 분리 설계를 화면과 API로 설명하기 쉬워짐

---

## 3.2 관리자 발매 / 재고 조회 고도화

DDIBS의 핵심 차별점은 `Launch` / `LaunchVariant` 중심 발매 처리 구조에 있다.  
따라서 V3에서는 이 점을 더 잘 보여주기 위해 발매 / 재고 운영 조회를 강화했다.

### 주요 개선 내용
- QueryDSL 기반 관리자 발매 조회 구현
- 검색 조건, 페이징, 정렬 지원
- 발매 코드 / 상태 / 판매자 ID / 상품명 / 기간 조건 조회 지원
- 발매별 옵션 수 / 총 재고 / 가용 재고 집계 응답 추가
- 관리자 발매 상세 조회에서 LaunchVariant 재고 현황 응답 구성
- 관련 통합 테스트 작성

### 의미
- DDIBS가 단순 주문 시스템이 아니라,
  **발매와 재고 운영 중심 시스템**이라는 점을 더 분명하게 보여줄 수 있게 됨
- `LaunchVariant`가 실제 재고 책임 엔티티라는 설계가 운영 조회를 통해 더 잘 드러남

---

## 3.3 최소 프론트엔드 데모 레이어 구축

V3에서 가장 눈에 띄는 변화는 React + Vite 기반의 관리자 프론트 데모 레이어를 추가한 점이다.

이 프론트는 화려한 서비스 UI가 아니라,
**DDIBS 백엔드 운영 API를 직접 시연하기 위한 최소 관리자 콘솔**을 목표로 했다.

### 주요 개선 내용
- React + Vite + TypeScript 프론트 프로젝트 생성
- 관리자 공통 레이아웃 구성
- 로그인 / 로그아웃 / 보호 라우트 적용
- 세션 기반 인증 흐름을 프론트와 연결
- 주문 조회 화면 구현
- 정산 조회 화면 구현
- 발매 / 재고 조회 화면 구현
- 공통 UI 컴포넌트 추가
    - `PageHeader`
    - `StatusBadge`
    - `LoadingBox`
    - `EmptyState`
    - `Pagination`
- 공통 포맷 유틸 추가
- 사이드바 active 상태 표시
- exact match 검색 안내 문구 정리

### 의미
- DDIBS가 “백엔드만 있는 프로젝트”가 아니라,
  **운영 API를 직접 시연 가능한 프로젝트**가 됨
- 면접 / 포트폴리오 상황에서 주문 / 정산 / 발매·재고 조회 흐름을 화면으로 바로 보여줄 수 있게 됨

---

## 3.4 local 전용 시연 데이터 초기화 기능 추가

프론트 데모를 실제로 검증하려면, 화면에 보일 시연용 데이터가 필요했다.  
V3에서는 이를 위해 local 프로필 전용 초기 데이터 생성 기능을 추가했다.

### 주요 개선 내용
- `application-local.yml`에 dev data 토글 추가
- `LocalDevDataInitializer` 추가
- `LocalDevDataService` 추가
- local 프로필에서만 동작하도록 분리
- 관리자 / 회원 / 판매자 / 상품 / 발매 / 주문 예시 데이터 생성
- 주문 상태 예시 구성
    - `CREATED`
    - `CONFIRMED`
    - `PAYMENT_FAILED`
- 결제 및 정산 생성 흐름 일부 재사용
- 프론트 주문/정산/발매 조회 화면에서 실제 row 렌더링 확인

### 의미
- 시연 시 매번 수동 데이터 준비를 하지 않아도 됨
- 프론트와 백엔드를 함께 검증하기 좋은 local 시연 환경이 생김
- 단순 fixture 삽입이 아니라, DDIBS 흐름을 살린 시연 데이터라는 점에서 설명 가능성이 높음

---

## 3.5 시연 문서 및 시퀀스 다이어그램 정리

V3 후반에는 구현뿐 아니라,
DDIBS를 어떻게 설명하고 시연할지에 대한 문서를 정리했다.

### 주요 개선 내용
- `DDIBS_DEMO_SCRIPT.md` 작성
- 로그인 → 주문 조회 → 정산 조회 → 발매/재고 조회 → 핵심 플로우 설명 순서 정리
- 시연 중 자주 나올 수 있는 질문과 답변 포인트 정리
- `DDIBS_SEQUENCE_DIAGRAMS.md` 작성
- 핵심 플로우 2개를 Mermaid 시퀀스 다이어그램으로 문서화
    - 주문 생성 → 홀드 → 결제 → 주문 확정 → 정산 생성
    - 홀드 만료 배치 → 주문 만료 → 재고 복구

### 의미
- DDIBS를 “만든 프로젝트”에서 끝내지 않고,
  **설명 가능한 포트폴리오**로 마감할 수 있게 됨
- 핵심 메시지를 면접 상황에서 짧고 강하게 전달하기 쉬워짐

## 4. V3에서 중요했던 설계 판단

## 4.1 프론트는 주인공이 아니라 시연 수단으로 둔다

V3에서 프론트를 도입했지만,
프로젝트의 중심은 여전히 백엔드였다.

따라서 프론트는
- 사용자용 서비스 화면 확장
- 과도한 상태 관리
- 화려한 UI 고도화

보다는,

- 로그인
- 관리자 운영 조회
- 시연 가능한 최소 화면

에 집중했다.

이 판단 덕분에 DDIBS의 정체성이 흐려지지 않았다.

---

## 4.2 운영 조회는 주문 → 정산 → 발매/재고 순으로 확장한다

운영 조회는 한 번에 전부 만들기보다,
이미 구축된 주문 조회 패턴을 기반으로 정산 조회, 발매/재고 조회로 확장하는 방식으로 진행했다.

이 방식은
- 구현 일관성
- QueryDSL 재사용 패턴
- 프론트 UI 흐름 통일

측면에서 더 실용적이었다.

---

## 4.3 시연 데이터도 local 전용으로 안전하게 분리한다

시연 데이터는 운영 코드와 섞지 않고,
- local 프로필
- property 토글
- idempotent 생성 방식

으로 분리했다.

이는 DDIBS가 정합성과 상태 전이를 중요하게 다루는 프로젝트인 만큼,
시연 편의를 위해 운영 구조를 어지럽히지 않으려는 판단이었다.

---

## 4.4 부분 검색과 상세 화면은 의도적으로 다음 단계 후보로 남겼다

V3 후반에는 아래 보강 후보도 있었다.

- 주문 / 정산 / 발매 코드 부분 검색
- 발매 상세 화면
- 정산 상세 화면

하지만 V3에서는
**프론트 데모의 핵심 가치를 넘지 않는 범위까지만 구현**하고,  
나머지는 후속 보강 후보로 남기기로 했다.

이 결정은 기능 부족 때문이 아니라,
**범위 통제와 백엔드 중심 포지셔닝 유지**를 위한 선택이었다.

## V2

- 배치 결과 구조화
- 관리자 주문 조회 API
- 테스트 구조 정리

## V3

즉 V2가 “프로젝트를 더 실무적으로 다듬는 단계”였다면,  
V3는 “그 프로젝트를 더 잘 보여주고 설명할 수 있게 만드는 단계”였다.

## 6. V3 기준 현재 강점

V3를 마친 현재 DDIBS의 강점은 아래와 같다.

- 핵심 플로우 2개가 완성되어 있다.
- 주문 생성 시 재고 홀드가 명확하게 구현되어 있다.
- 결제 성공 / 실패 / 홀드 만료 시 상태 전이가 정책적으로 보호된다.
- 동시 주문 과판매 방지를 통합 테스트로 검증했다.
- 결제 vs 홀드 만료 배치 경합을 통합 테스트로 검증했다.
- Testcontainers 기반으로 테스트 재현성을 확보했다.
- 관리자 주문 / 정산 / 발매·재고 조회를 운영 관점에서 제공한다.
- 최소 프론트 데모 레이어를 통해 직접 시연 가능하다.
- local 시연 데이터를 통해 실제 row를 바로 확인할 수 있다.
- 시연 문서와 시퀀스 다이어그램으로 설명 가능성이 높아졌다.

즉 DDIBS는
단순 CRUD 포트폴리오가 아니라,
**정합성·동시성·상태 전이·운영 조회·시연 가능성**을 갖춘 백엔드 포트폴리오로 자리잡았다.

이 항목들은 DDIBS의 핵심을 해치지 않는 범위에서,

## 8. 회고

V3에서 가장 중요했던 점은,
DDIBS를 단순히 “구현된 프로젝트”에서 멈추지 않고
**실제로 보여주고 설명할 수 있는 프로젝트**로 바꾼 것이다.

주문 / 정산 / 발매·재고 운영 조회를 관리자 API와 프론트 화면으로 연결하면서,
DDIBS의 차별점이 더 직접적으로 드러나기 시작했다.

특히 발매/재고 조회 화면은
`LaunchVariant` 중심 재고 구조를 시각적으로 보여준다는 점에서,
DDIBS가 왜 일반적인 쇼핑몰이 아닌지 설명하는 데 큰 도움이 되었다.

또한 local 시연 데이터와 시연 스크립트를 정리하면서,
DDIBS는 “좋은 코드”를 넘어서
**면접과 포트폴리오 상황에서 실제로 활용 가능한 결과물**로 다듬어졌다.

---

## 9. 한 줄 결론

DDIBS V3는 관리자 정산 조회, 발매/재고 운영 조회, 최소 프론트 데모 레이어, 시연 문서 정리를 통해  
프로젝트를 **실제로 보여주고 설명할 수 있는 백엔드 포트폴리오**로 마감한 단계였다.
