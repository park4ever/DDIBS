# DDIBS Demo Script

## 1. 문서 목적

이 문서는 DDIBS 시연 시 **어떤 순서로 화면을 보여주고, 각 장면에서 무엇을 설명할지** 정리한 실전용 스크립트다.

DDIBS는 일반 쇼핑몰이 아니라, **한정 수량 발매 상황에서 주문, 재고 홀드, 홀드 만료 복구, 결제 확정, 정산 생성, 관리자 운영 조회**까지를 안정적으로 처리하는 백엔드 시스템이다.

따라서 시연도 기능 수를 나열하기보다 아래 메시지를 전달하는 데 집중한다.

- 발매 가능 여부 검증
- 주문 생성 시 재고 홀드
- 결제 성공/실패에 따른 상태 전이
- 홀드 만료 시 자동 복구
- 확정 주문 기준 정산 생성
- 관리자 관점의 주문 / 정산 / 발매·재고 운영 조회

---

## 2. 시연 목표

시연의 목표는 아래 3가지를 짧고 분명하게 보여주는 것이다.

1. **DDIBS는 단순 CRUD 쇼핑몰이 아니라 고수요 발매 처리 시스템이다.**
2. **핵심 플로우 2개가 실제 코드와 테스트로 검증되어 있다.**
3. **관리자 운영 조회와 프론트 데모를 통해 시연 가능한 상태다.**

## 6. 상세 시연 스크립트

## 6.1 프로젝트 소개

### 보여줄 것
- README 또는 프로젝트 소개 화면
- 프로젝트 한 줄 소개

### 말할 내용
> DDIBS는 한정 수량 상품 발매 상황에서 주문 생성 시 재고를 홀드하고,  
> 결제 성공/실패와 홀드 만료에 따라 재고를 정확히 복구하며,  
> 확정 주문 기준으로 정산까지 생성하는 Java/Spring 백엔드 드롭 런치 플랫폼입니다.

> 일반 쇼핑몰처럼 기능 수를 늘리는 프로젝트가 아니라,  
> 고수요 발매 상황에서 중요한 **정합성, 동시성 제어, 상태 전이, 운영 조회**를 보여주는 데 집중했습니다.

### 핵심 포인트
- “쇼핑몰”보다 “드롭 런치 처리 시스템”이라는 점 강조
- 기능 수보다 정합성과 설명 가능성이 핵심이라는 점 강조

## 6.2 로그인

### 보여줄 것
- `/login`
- 관리자 로그인 화면
- 로그인 성공 후 `/admin/orders` 이동

### 말할 내용
> 프론트는 React + Vite 기반의 최소 관리자 데모 레이어로 구성했습니다.  
> 프론트 자체가 주인공은 아니고, 백엔드 운영 API를 직접 시연하기 위한 화면입니다.

> 로그인은 Spring Security의 세션 기반 인증을 사용하고,  
> 관리자 화면은 보호 라우트로 감싸서 인증되지 않은 상태에서는 접근할 수 없도록 했습니다.

### 체크 포인트
- 로그인 성공
- 로그아웃 버튼 존재
- 보호 라우트 동작 설명 가능

## 6.3 관리자 주문 조회

### 보여줄 것
- `/admin/orders`
- 실제 주문 row
- 상태 배지
- 필터 입력
- 페이지네이션

### 예시 시연 흐름
1. 주문 목록 기본 조회
2. 주문 상태 `CONFIRMED`로 필터
3. 판매자 ID 또는 회원 ID로 필터
4. 정확한 주문 코드로 검색
5. 다시 초기화

### 말할 내용
> 주문 조회 화면은 운영자가 주문 상태와 추적 정보를 확인하기 위한 관리자 화면입니다.

> QueryDSL 기반으로 주문 코드, 주문 상태, 판매자 ID, 회원 ID, 회원 이메일, 상품명, 기간 조건을 조합해서 조회할 수 있습니다.

> 여기서 중요한 건 단순 조회보다,  
> 이 주문들이 모두 **발매 가능 여부 검증 → 주문 생성 → 홀드 생성 → 결제 결과 반영** 흐름을 거쳐 만들어진 데이터라는 점입니다.

### 핵심 포인트
- `CREATED`, `CONFIRMED`, `PAYMENT_FAILED` 상태를 화면에서 보여주기
- exact match 안내 문구가 있는 이유 설명 가능
- local dev data로 프론트 검증했다는 점 언급 가능

## 6.4 관리자 정산 조회

### 보여줄 것
- `/admin/settlements`
- 정산 코드 / 주문 코드 / 판매자 ID / 상태 필터
- 정산 금액 / 상태 / 생성 시각

### 예시 시연 흐름
1. 정산 목록 기본 조회
2. 상태 `CREATED` 또는 `CONFIRMED` 필터
3. 판매자 ID 필터
4. 정확한 정산 코드 또는 주문 코드 검색

### 말할 내용
> DDIBS는 결제 성공 시점에 정산을 바로 만드는 대신,  
> 확정 주문 기준으로 별도 배치가 정산을 생성하도록 분리했습니다.

> 이렇게 하면 결제 플로우의 책임을 줄일 수 있고,  
> 정산 생성은 운영 배치의 성격으로 더 명확하게 설명할 수 있습니다.

> 정산 조회 화면은 그 결과를 운영자가 추적할 수 있도록 만든 관리자 화면입니다.

### 핵심 포인트
- “결제와 정산 생성을 분리했다”는 설계 판단 강조
- 정산 배치 멱등성 구조와 운영 로그 개선을 언급 가능

## 6.5 관리자 발매 / 재고 조회

### 보여줄 것
- `/admin/launches`
- 발매 코드 / 상태 / 판매자 ID / 상품명 / 기간 필터
- 발매 상태
- 옵션 수 / 총 재고 / 가용 재고

### 예시 시연 흐름
1. 발매 목록 기본 조회
2. 상품명 부분 검색
3. 상태 `OPEN` 필터
4. 발매별 옵션 수 / 총 재고 / 가용 재고 비교

### 말할 내용
> DDIBS에서 실제 주문과 재고 차감의 기준은 `ProductVariant`가 아니라 `LaunchVariant`입니다.

> 즉 상시 판매 재고가 아니라,  
> **이번 발매에서 실제로 열린 판매 단위와 재고**를 중심으로 시스템을 설계했습니다.

> 그래서 발매/재고 조회 화면은 DDIBS의 정체성을 가장 잘 보여주는 운영 화면입니다.

### 핵심 포인트
- `LaunchVariant` 중심 재고 관리 설명
- 상품명은 부분 검색, 코드 검색은 정확 일치라는 UX 차이도 설명 가능
- DDIBS가 단순 주문 시스템이 아니라 발매 운영 시스템이라는 점 강조

## 6.6 핵심 백엔드 플로우 설명

여기부터는 화면 시연만 하지 말고, **프로젝트의 핵심 메시지**를 짧게 설명한다.

### 플로우 1
**발매 조회 → 발매 가능 여부 검증 → 주문 생성(재고 홀드) → 결제 → 주문 확정 → 정산 생성**

### 말할 내용
> 주문 생성 시점에 바로 홀드를 만들고, `LaunchVariant.availableStock`을 감소시켜  
> 결제 전 일정 시간 동안 재고를 임시 선점합니다.

> 결제 성공 시에는  
> `Payment.SUCCESS`, `Order.CONFIRMED`, `HoldReservation.CONSUMED`로 상태가 전이되고,  
> 이후 정산 배치가 확정 주문을 기준으로 정산을 생성합니다.

### 플로우 2
**홀드 만료 배치 → 자동 해제 → 주문 만료 처리 → 재고 복구**

### 말할 내용
> 홀드 TTL이 지난 경우에는 배치가 만료 대상을 찾아  
> `HoldReservation.EXPIRED`, `Order.HOLD_EXPIRED`, `availableStock 복구`를 수행합니다.

> 이 흐름을 통해 결제 미완료 상태가 재고를 계속 점유하지 않도록 했습니다.

## 6.7 테스트와 정합성 / 동시성 설명

### 보여줄 것
- 테스트 목록 또는 README 일부
- 필요하면 테스트 클래스명만 간단히 소개

### 말할 내용
> DDIBS는 단순 happy path 테스트가 아니라,  
> 실패/복구/경합 시나리오를 통합 테스트로 검증하는 데 집중했습니다.

> 예를 들면
> - 재고 1건 상황 동시 주문
> - 결제 성공 vs 홀드 만료 배치 경합
    > 같은 시나리오를 실제로 검증했습니다.

> 특히 결제와 홀드 만료 배치가 거의 동시에 실행되는 상황에서  
> 최종 상태가 섞이지 않고 정책적으로 일관된 종결 상태로만 수렴하도록 리팩토링하고 테스트로 확인했습니다.

### 핵심 포인트
- “동시성 문제를 그냥 말로만 적은 게 아니라 테스트로 검증했다” 강조
- DDIBS의 차별점은 이 부분에 있다는 점 명확히 전달

## 6.8 마무리

### 말할 내용
> DDIBS는 일반적인 CRUD 쇼핑몰이 아니라,  
> 한정 수량 발매 상황에서 재고 홀드, 만료 해제, 결제 확정, 정산 생성, 관리자 운영 조회까지를  
> **정합성·동시성·상태 전이 중심으로 설계한 백엔드 시스템**입니다.

> 핵심 플로우를 완성한 뒤,  
> 테스트 재현성, 배치 운영성, 관리자 조회, 프론트 데모까지 보강하면서  
> 단순 기능 나열형 포트폴리오가 아니라 설명 가능한 시스템 형태로 다듬었습니다.

## 7. 시연 시 자주 나올 수 있는 질문과 답변 포인트

### Q1. 왜 결제 성공 시 정산을 바로 만들지 않았나요?
- 결제 플로우의 책임을 줄이기 위해
- 정산은 운영 배치 성격이 더 강해서 분리
- 확정 주문 기준 생성이 더 설명 가능

### Q2. 왜 재고를 ProductVariant가 아니라 LaunchVariant가 가지나요?
- DDIBS는 상시 판매 시스템이 아니라 발매 시스템
- 실제 판매가와 재고는 “이번 발매에서 열린 단위”가 책임지는 게 맞음

### Q3. 동시 주문에서 과판매는 어떻게 막았나요?
- 주문 생성 시 `LaunchVariant`를 비관적 락으로 조회
- 재고 1건 상황에서 1건만 홀드 생성 성공하도록 검증
- 통합 테스트로 확인

### Q4. 홀드 만료와 결제 성공이 겹치면 어떻게 되나요?
- 락 순서 통일
- 최신 상태 재검증
- 경합 테스트로 일관된 최종 상태 확인

### Q5. 왜 프론트를 붙였나요?
- 프론트 자체가 주인공은 아님
- 백엔드 운영 API를 직접 시연할 수 있게 하려는 최소 관리자 데모 레이어
- 주문 / 정산 / 발매·재고 운영 조회를 눈으로 보여주기 위함

## 9. 한 줄 결론

DDIBS 시연은 기능을 많이 보여주는 것이 아니라,  
**고수요 발매 상황을 안정적으로 처리하는 백엔드 시스템이라는 메시지**를  
로그인 → 운영 조회 → 핵심 플로우 설명 → 테스트 근거 순서로 전달하는 데 집중해야 한다.
