# DDIBS V5 Plan

## 1. 문서 목적

이 문서는 DDIBS V5에서 무엇을 점검하고, 무엇을 개선할지 정리한 계획 문서다.

V4까지의 DDIBS는
- 핵심 플로우 2개 완성
- 동시성 / 경합 통합 테스트 확보
- 관리자 주문 / 정산 / 발매·재고 조회
- 관리자 발매 상세 / 정산 상세
- 프론트 데모 레이어
- 시연 문서 / 최종 리뷰 문서

까지 정리되었다.

즉 V4까지는 **동작하고, 보여줄 수 있고, 설명할 수 있는 상태**를 만드는 데 집중했다면,  
V5는 그 위에 **백엔드 정책 점검과 안정성 보강**을 더하는 단계로 정의한다.

V5의 핵심은 새로운 화면을 늘리거나 범용 커머스 기능을 추가하는 것이 아니라,  
DDIBS의 본체인 **정합성 · 동시성 · 상태 전이 · 배치 운영성**을 한 번 더 점검하고 다듬는 데 있다.

---

## 2. V5 목표

V5의 목표는 아래 4가지다.

1. **시간/상태/배치 정책의 경계 조건을 더 명확하게 만든다.**
2. **배치 트랜잭션 경계를 재점검해 온라인 플로우와의 간섭을 줄인다.**
3. **락 획득 순서를 실제 코드 기준으로 검증하고 표준화한다.**
4. **운영 장애/재실행 상황에서 더 설명 가능한 테스트와 로그를 보강한다.**

정리하면 V5는  
“기능 확장”보다 **백엔드 정책 감사 + 최소 수정 기반 구조 보강** 단계다.

---

## 3. V5 방향 요약

### V5에서 집중할 것
- 홀드 만료 경계시각 정책 정리
- 배치 트랜잭션 경계 재설계
- write 경로별 락 획득 순서 점검
- 부분 실패 후 재실행 테스트 보강
- 운영 로그 / 예외 추적성 보강

### V5에서 지금 하지 않을 것
- 장바구니
- 쿠폰 / 포인트
- 배송 / 송장
- 환불 / 교환
- 실제 PG 연동
- 사용자용 풀 커머스 프론트
- 프론트 화면 대규모 확장
- Kafka / MQ / MSA / K8s
- 기능 수를 늘리기 위한 불필요한 서브도메인 추가

즉 V5도 여전히  
**DDIBS의 핵심 문제를 더 날카롭게 다듬는 방향**으로 간다.

---

## 4. Codex 리뷰 반영 원칙

V5는 외부 리뷰 결과를 그대로 수용하는 단계가 아니다.  
Codex 리뷰는 참고 자료로 사용하되, DDIBS 기준으로 다시 우선순위를 정해 반영한다.

### 반영 기준
1. 정합성과 동시성에 직접 영향이 있는가
2. 상태 전이 / 배치 정책의 설명력을 높이는가
3. 현재 구조를 유지한 채 최소 수정으로 개선 가능한가
4. 테스트로 증명 가능한가

### 이번 V5에서의 판단
- **우선 반영**
    - H2 만료 경계시각 정책
    - M1 배치 트랜잭션 경계
    - H1 락 순서 재검증 및 표준화
- **후순위 보류**
    - contains 검색 성능 정책
    - 코드 생성 정책 공통화
    - 과도한 공통화 / 추상화
- **보강 후보**
    - 부분 실패 후 재실행 테스트
    - 운영 로그 구조화

즉 V5는 Codex 리뷰를 바탕으로 하되,  
**DDIBS 핵심 흐름과 직접 연결되는 항목만 선별적으로 반영**한다.

## 5. In Scope

## 5.1 홀드 만료 경계시각 정책 정리
우선순위: 상

문제의식:
- `expiresAt == now`인 경우를 만료로 볼지 말지 정책이 애매하면
  도메인 / 쿼리 / 배치 / 테스트가 어긋날 수 있다.
- 경계시각이 모호하면 재고 복구 시점과 운영 조회 설명력이 떨어진다.

목표:
- 만료 판정 기준을 명문화한다.
- 도메인 / 리포지토리 쿼리 / 테스트를 같은 기준으로 맞춘다.
- 필요 시 `Clock` 주입으로 시간 비교 기준을 통일한다.

예상 작업:
- `HoldReservation.isExpiredAt` 점검
- 만료 대상 조회 쿼리 점검
- 경계시각 테스트 추가
    - `now == expiresAt`
    - `now < expiresAt`
    - `now > expiresAt`

의미:
- 시간 경계 조건이 설명 가능해진다.
- 만료 / 재고 복구 / 운영 조회 사이의 정합성이 좋아진다.

---

## 5.2 배치 트랜잭션 경계 재설계
우선순위: 상

문제의식:
- 홀드 만료 배치와 정산 생성 배치가 루프 전체 단일 트랜잭션이라면
  락 점유 시간과 롤백 범위가 과도할 수 있다.
- 이는 온라인 주문/결제 흐름과 간섭할 가능성을 높인다.

목표:
- 배치의 읽기 단계와 처리 단계를 분리할지 점검한다.
- 필요하면 건별 처리 또는 chunk 단위 처리로 트랜잭션 범위를 축소한다.
- 부분 실패 시 전체 롤백 대신 “스킵 후 계속” 구조가 더 명확히 드러나게 만든다.

예상 작업:
- `HoldExpirationBatchService` 트랜잭션 경계 점검
- `SettlementBatchService` 트랜잭션 경계 점검
- 읽기 / 처리 분리 구조 검토
- 부분 실패 / 재실행 테스트 보강

의미:
- 배치가 온라인 흐름을 덜 방해하게 된다.
- 실패 복구와 재실행 설명이 쉬워진다.

---

## 5.3 write 경로별 락 획득 순서 재검증 및 표준화
우선순위: 상

문제의식:
- 락 순서 문제는 실제 데드락으로 이어질 수도 있고,
  아직 실제 충돌은 없더라도 미래 write 경로 확장 시 위험 요인이 될 수 있다.
- 다만 추측 기반으로 구조를 크게 바꾸기보다, 현재 코드 기준으로 먼저 검증해야 한다.

목표:
- 현재 write 경로별 락 획득 순서를 표로 정리한다.
- 실제 충돌 가능성이 있는지와 예방 차원의 표준화 필요성을 구분한다.
- DDIBS 전역의 “재고 관련 write 경로 락 순서 원칙”을 정한다.

예상 작업:
- 주문 생성
- 결제 성공 / 실패
- 홀드 만료 배치
- 정산 생성 배치
- 기타 재고 복구 / 상태 변경 write 경로

에 대해 락 순서를 정리하고 비교한다.

의미:
- 데드락 위험을 추측이 아니라 근거 기반으로 다룰 수 있다.
- 이후 기능 추가 시 설명 가능한 규칙이 생긴다.

---

## 5.4 부분 실패 후 재실행 테스트 보강
우선순위: 중

문제의식:
- 배치 멱등성 테스트는 존재하지만,
  실제 운영에서는 “중간 실패 → 재실행” 시나리오가 더 중요하다.
- 중단 후 재기동 상황에서 상태 / 재고 / 정산 생성이 일관되게 수렴해야 한다.

목표:
- 홀드 만료 배치와 정산 생성 배치에 대해
  부분 실패 후 재실행 시나리오를 테스트로 보강한다.

예상 작업:
- 실패 주입 기반 테스트 추가
- 일부 건 처리 후 예외 발생
- 재실행 후 최종 상태 / 재고 / 중복 생성 무결성 검증

의미:
- 운영 재실행 안정성을 더 명확하게 증명할 수 있다.

---

## 5.5 운영 로그 / 예외 추적성 보강
우선순위: 중

문제의식:
- 500 응답 통일만으로는 실제 운영 원인 추적에 한계가 있다.
- DDIBS는 정합성/동시성 이슈가 중요한 프로젝트이므로,
  장애 시 원인 추적성이 중요하다.

목표:
- 공통 예외 처리에서 구조화 로그의 최소 기준을 정한다.
- URI, ErrorCode, trace/context 정보 등 운영 추적에 필요한 정보를 정리한다.

예상 작업:
- `GlobalExceptionHandler` 점검
- 공통 로그 필드 기준 정리
- 강제 예외 발생 시 로그 확인 테스트 또는 수동 점검 시나리오 정리

의미:
- 장애 분석과 회고 설명력이 좋아진다.

## 6. Backlog / 후보 항목

아래는 V5 핵심 범위에는 바로 넣지 않지만, 기억해둘 후보들이다.

### 6.1 주문 상세 페이지
- 주문 상태 / 결제 상태 / 홀드 상태를 한 화면에서 보여주는 운영 상세
- DDIBS 핵심 상태 전이를 설명하기 좋은 프론트 보강 후보

판단:
- 가치가 높다.
- 그러나 V5 핵심은 백엔드 점검이므로, 이번 버전에서는 후순위로 둔다.

### 6.2 contains 검색 정책 / 인덱스 재점검
- 코드 / 이메일 / 상품명 contains 검색의 성능 점검
- prefix 검색과의 병행 여부 검토

판단:
- 운영 성능 측면에서 의미는 있지만, 지금은 정책/트랜잭션/락이 더 우선이다.

### 6.3 코드 생성 정책 공통화
- 주문 코드 / 결제 코드 / 정산 코드 생성 정책 일관화

판단:
- 나쁜 후보는 아니지만, 지금은 핵심 안정성 문제보다 후순위다.

## 9. V5 완료 기준

V5는 아래 조건을 만족하면 마감으로 본다.

- 홀드 만료 경계시각 정책이 문서/코드/테스트로 일치한다.
- 배치 트랜잭션 경계가 현재보다 더 설명 가능하게 정리된다.
- write 경로별 락 획득 순서가 표로 정리되고, 최소한의 표준 원칙이 문서화된다.
- 부분 실패 후 재실행 시나리오가 테스트로 보강된다.
- 운영 예외 / 로그 추적성이 현재보다 개선된다.

즉 V5는  
**백엔드의 시간 정책, 배치 정책, 락 정책을 더 단단하게 만드는 단계**다.

프로젝트의 백엔드 완성도를 한 단계 더 높이는 단계다.
